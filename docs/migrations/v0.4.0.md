# Upgrading to v0.4.0

The `Status` RPC returns gRPC `Unavailable` when PostgreSQL or queue inspection fails.

## Do I need to act?

**Required** if your caller reads a degraded response after a successful RPC. Check the returned error before accessing the response. Treat any RPC error as not ready; use a deadline for the call.

## Handle readiness failures

Previously, PostgreSQL failure could produce a successful response with a down dependency. A successful `Status` call now means PostgreSQL and queue inspection both succeeded. Failure returns `Unavailable` with a generic message and no successful response payload.

The healthy response retains its PostgreSQL report and queue backlog. Queue size does not introduce a readiness threshold. Use `UnaryEcho` for process-only liveness.

## Roll out and verify

Deploy the service before simplifying consumers to rely only on RPC success. Keep dependency-status checks while older instances can still serve requests; updating the Go client does not update those instances.

In a test environment, verify a successful call with healthy dependencies and `Unavailable` when PostgreSQL or queue inspection fails. Confirm that a healthy response includes the queue report, even with an empty queue, and that `UnaryEcho` remains successful while the process is running.

No secret rotation or database migration is required by this health-check change.
