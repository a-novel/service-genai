# Upgrading to v0.5.0

You still build the provider's request; the service now runs it without a worker. Submitting starts the provider call, each `GenerationGet` checks a stale generation with the provider, and the new `sweep` server, which a scheduler calls, checks the generations nobody polled. Every attempt's raw provider response comes back on the generation.

## Do I need to act?

**Required** for callers: the submit request and the generation change shape, `GenerationWatch` and `UsageQuery` are removed, and the service no longer sends `store: false` for you.

**Required** for operators: the database schema is replaced, the worker and reaper settings are removed, `OPENAI_API_KEY` becomes mandatory, and the new `sweep` image needs a scheduler.

## Submit the provider's request

| Removed from `GenerationSubmitRequest`  | Replacement                                                                                                                                                                                                                                                                                                                                                                                    |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `request`, the OpenAI Responses payload | `payload`, the same request body, and `provider` (`openai`), which names the connector that runs it. The connector writes `background: true` and `stream` over the payload and forwards the rest.                                                                                                                                                                                              |
| `max_attempts`                          | The `MAX_ATTEMPTS` service setting (`2`). v0.4.0 ran a request once unless you raised `max_attempts`: set `MAX_ATTEMPTS=1` to keep that.                                                                                                                                                                                                                                                       |
| `idempotency_key`                       | Nothing: the service derives the key from the owner, the purpose, the provider, `stream`, the payload and the `variant`. To recover after a crash, resend the same request within `RETENTION` (6 hours by default, 7 days before): past it, the generation is purged with its key, and a resend runs it again. To ask for another result of a request that succeeded, send the next `variant`. |

A failed or cancelled generation is not served again: resending its request runs it from scratch. Drop any key you persisted for crash recovery, and anything in your payload that changes between resends, such as a timestamp: the same request is the same call. Formatting and the order of top-level fields do not matter; the order of nested fields does, since a provider can read meaning into it, such as a schema's property order.

The payload must be a JSON object of at most 16 MiB, about 3.5 million tokens of prose, and I-JSON ([RFC 7493](https://www.rfc-editor.org/rfc/rfc7493)): valid UTF-8, no unpaired surrogates, no duplicate names in an object. A request more than 64 KiB past that limit is refused by the gRPC transport, with `RESOURCE_EXHAUSTED` and no cap named, so check the size before sending. `purpose` stays required, and must now be declared in the service's caps file; an undeclared purpose answers `INVALID_ARGUMENT`. Send your user's `user_tier` to select the caps it answers to. Once a user's token usage has reached a cap, or the user already has as many generations in flight as its tier allows, for the purpose or across all of them (pending or running, and for the purpose also failed within the last 15 minutes with a call nothing metered: a start the provider may have accepted, a response over 24 MiB, or a stop that never took), a submit that would create a generation answers `RESOURCE_EXHAUSTED`, naming the limit; resending a pending, running or succeeded request still attaches to it. A request that breaks a rule, or names a provider with no connector, answers `INVALID_ARGUMENT` with the reason. A generation still running 2 hours after its start is stopped and fails.

## Send the privacy fields yourself

v0.4.0 always sent `store: false` and its own `metadata`, over yours. v0.5.0 forwards both as you send them, and OpenAI keeps a response for 30 days when `store` is left out. Send `store: false` in every payload whose prose must stay out of OpenAI's copy.

## Read the generation

| Removed from `Generation`         | Replacement                                                                                                                                                                  |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `output`, the provider's envelope | `attempts`: every provider call that reached an answer, retried and cancelled ones included, with the provider's raw response. The last attempt's response holds the output. |
| `attempt`, `max_attempts`         | `attempts`.                                                                                                                                                                  |

`provider` is new and echoes the submission. A response is at most 24 MiB: one larger fails its generation, which can happen only when you ask for more than the text, such as log probabilities. OpenAI echoes your `instructions` in every response, so keep a large context in `input`, which it does not. `GENERATION_STATUS_SUCCEEDED` means the provider finished the call: an output cut at your `max_output_tokens`, or a refusal, is a succeeded generation whose response says so. `GENERATION_STATUS_FAILED` means the generation holds no finished response, and `error` says why in the service's words. `error` now names why a generation was cancelled too, so read `status`, not `error`, to tell a failure. A request the provider rejected comes back failed, with the provider's error body as its attempt's response.

## Cancel is idempotent

Cancelling a generation that already settled returns it as it stands, with `OK`, instead of `NOT_FOUND`. A retried cancel, or one that lost a race with completion, still succeeds: read the returned status to know whether it was cancelled. `NOT_FOUND` now means only that the owner has no such generation.

A cancel also acts before it answers. It settles a generation whose call never started, and stops a running call with the provider, so the status it returns is usually `CANCELLED` already. A generation whose start is in flight is marked, and the check that sees the call land stops it.

## Poll instead of watching

`GenerationWatch` is removed: poll `GenerationGet` on your own interval until the generation settles. A polled generation moves at the caller's pace; an unpolled one waits for the sweep, up to one `SWEEP_INTERVAL`. A submit waits up to 20 seconds for the provider to accept its call, and a poll up to 10 for the provider's answer: give both a deadline of at least 25 seconds, since a check whose caller left resumes only with the server's next request.

## Stream the output as it is written

To show a generation's output while the provider writes it, submit it with `stream: true`, then call `GenerationStream` with its id. The stream forwards the provider's events, as sent, with their `sequence_number`, and ends after the terminal one. After a disconnect, open a new stream with `starting_after` set to the last sequence number you received. The provider streams a call for 5 minutes after its creation: past that, or for a generation not submitted with `stream`, the stream answers `FAILED_PRECONDITION`, and you read the result with `GenerationGet`. A streamed submit answers once the provider has begun the call, so it takes the provider's queue time, as does a poll that starts the call again after the provider turned one away: give both a deadline of at least 35 seconds. `stream` is part of the request: the same payload with and without it are two generations. A streamed generation is one provider call: a retryable provider failure settles it failed rather than retrying it, so resend it to run it again.

## Read usage off the responses

`UsageQuery` is removed. Each attempt's response carries the usage the provider reported for it: read it there before the attempts are purged with their generation. The service keeps its own permanent Usage Record of every answered attempt, which the caps sum, and exposes none of it through the API.

## Update the Go client

The Go client follows the API: `GenerationWatchRequest`, `GenerationWatchResponse`, `UsageQueryRequest`, `UsageQueryResponse`, `UsageGroup`, `UsageTotal` and `GenerationStatusAbandoned` are removed. So are `ExtractResponsesOutputText` and its errors, `ErrResponsesOutputEmpty`, `ErrResponsesOutputMalformed`, `ErrResponsesOutputTextMissing` and `ErrResponsesRefused`: decode the last attempt's response with your provider's SDK, such as openai-go's `responses.Response` and its `OutputText()`.

`NewClient` raises its receive limit to 64 MiB, which two 24 MiB responses need. A caller that dials its own connection sets `grpc.MaxCallRecvMsgSize` to at least that.

## Recreate the database

The migration history starts over in this release. No environment ran service-genai before it, so there is no data to carry over: start the `database` image on a fresh volume, then run the migrations job. A data directory from the earlier image is not portable to the new one, and lacks the settings the retention purge needs.

## Replace the configuration

| Removed                                                                                     | Replacement                                                                                          |
| ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `WORKER_ID`, `WORKER_INTERVAL`, `WORKER_LEASE`, `WORKER_BATCH_SIZE`, `WORKER_POLL_INTERVAL` | `CHECK_INTERVAL` (`2s`)                                                                              |
| `REAPER_INTERVAL`, `REAPER_GRACE`, `REAPER_BATCH_SIZE`                                      | `SWEEP_INTERVAL` (`1m`), `SWEEP_BATCH_SIZE` (`50`)                                                   |
| —                                                                                           | `MAX_ATTEMPTS` (`2`), replacing the request's `max_attempts`                                         |
| `RETENTION` default `168h`                                                                  | `RETENTION` default `6h`: a settled generation, its attempts and its request key are purged together |
| `GRPC_PING`                                                                                 | Nothing: the health check reports the server's status as it changes, with no refresh interval        |
| —                                                                                           | `GRPC_TIMEOUT_SHUTDOWN` (`8s`), where v0.4.0 drained without a bound                                 |

`OPENAI_API_KEY` keeps its name and is now required: the servers refuse to start without it. They also refuse a `RETENTION` under `15m`, a `SWEEP_INTERVAL` over `5m`, a `SWEEP_BATCH_SIZE` outside 1 to 100 and a `MAX_ATTEMPTS` outside 1 to 2. `GRPC_TIMEOUT_SHUTDOWN` fits inside Cloud Run's ten seconds between SIGTERM and SIGKILL: keep any override under your orchestrator's kill delay.

## Schedule the sweep

The reaper becomes the `sweep` image. Deploy it privately, and have a scheduler `POST /sweep` every `SWEEP_INTERVAL`, as the [README](../../README.md#deploying) explains. Each call checks every generation nobody checked within half of `SWEEP_INTERVAL`, so a late call skips none. Without the sweep, a generation nobody polls settles only on a provider notification, and one waiting to retry its start never does, keeping its owner's concurrency slot. No server runs work outside a request any more, so none needs CPU between them. The REST servers default `REST_TIMEOUT_REQUEST` to `2m` and `REST_TIMEOUT_WRITE` to `2m15s`, which a sweep's answer needs.

## Settle generations on provider notifications (optional)

The new `rest` image checks a generation the moment its provider reports the call ended, instead of on the next poll or sweep. Deploy it publicly with `OPENAI_WEBHOOK_SECRET` and register the OpenAI webhook endpoint, as the [README](../../README.md#deploying) explains. Without it, polls and the sweep settle every generation as before.

## Status changes

`GENERATION_STATUS_ABANDONED` is removed. A generation whose process died is picked up by the next check instead.

## Roll out and verify

A rolling deploy is safe at any time: a check runs for seconds, and anything it did not finish is redone by the next one. The exception is a start the provider has not answered when its process stops: the call may run unread, so its generation fails at the first poll or sweep a minute after the start, its outcome unknown, and holds a concurrency slot of its purpose for 15 minutes.

In a test environment, submit a generation, stop the server while it runs, start it again, and poll: the generation settles once, with one attempt per answered provider call.
