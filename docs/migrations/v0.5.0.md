# Upgrading to v0.5.0

You still build the provider's request; the service now runs it without a worker. Submitting starts the provider call, each `GenerationGet` checks a stale generation with the provider, and a sweep checks the generations nobody polled. Every attempt's raw provider response comes back on the generation.

## Do I need to act?

**Required** for callers: the submit request and the generation change shape, and `GenerationWatch` and `UsageQuery` are removed.

**Required** for operators: the database schema is replaced, the worker and reaper settings are removed, and `OPENAI_API_KEY` becomes mandatory.

## Submit the provider's request

| Removed from `GenerationSubmitRequest`  | Replacement                                                                                                                                                                                                                        |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `request`, the OpenAI Responses payload | `payload`, the same request body, and `provider` (`openai`), which names the connector that runs it. The connector writes `background: true` and `stream` over the payload and forwards the rest.                                  |
| `max_attempts`                          | The `MAX_ATTEMPTS` service setting (`2`).                                                                                                                                                                                          |
| `idempotency_key`                       | Nothing: the service derives the key from the owner, the purpose, the provider and the payload. To recover after a crash, resend the same request. To ask for another result of a request that succeeded, send the next `variant`. |

A failed or cancelled generation is not served again: resending its request runs it from scratch. Drop any key you persisted for crash recovery, and anything in your payload that changes between resends, such as a timestamp: the same request is the same call. Formatting and the order of top-level fields do not matter; the order of nested fields does, since a provider can read meaning into it, such as a schema's property order.

The payload must be a JSON object of at most 3,688,000 bytes, and I-JSON ([RFC 7493](https://www.rfc-editor.org/rfc/rfc7493)): valid UTF-8, no unpaired surrogates, no duplicate names in an object. `purpose` stays required, and must now be declared in the service's caps file; an undeclared purpose answers `INVALID_ARGUMENT`. Send your user's `user_tier` to select the caps it answers to. Once a user's token usage has reached a cap, or the user already has as many generations in flight as its tier allows, for the purpose or across all of them (pending, running, or failed within the last 15 minutes with a start the provider may have accepted), a submit that would create a generation answers `RESOURCE_EXHAUSTED`, naming the limit; resending a running or succeeded request still attaches to it. A request that breaks a rule, or names a provider with no connector, answers `INVALID_ARGUMENT` with the reason. A generation still running 2 hours after its start is stopped and fails. The privacy fields are yours to set: send `store: false` to keep the prose out of OpenAI's 30-day copy.

## Read the generation

| Removed from `Generation`         | Replacement                                                                                                                                                                  |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `output`, the provider's envelope | `attempts`: every provider call that reached an answer, retried and cancelled ones included, with the provider's raw response. The last attempt's response holds the output. |
| `attempt`, `max_attempts`         | `attempts`.                                                                                                                                                                  |

`provider` is new and echoes the submission. `GENERATION_STATUS_SUCCEEDED` means the provider finished the call: an output cut at your `max_output_tokens`, or a refusal, is a succeeded generation whose response says so. `GENERATION_STATUS_FAILED` means the generation holds no finished response, and `error` says why in the service's words. A request the provider rejected comes back failed, with the provider's error body as its attempt's response.

## Cancel is idempotent

Cancelling a generation that already settled returns it as it stands, with `OK`, instead of `NOT_FOUND`. A retried cancel, or one that lost a race with completion, still succeeds: read the returned status to know whether it was cancelled. `NOT_FOUND` now means only that the owner has no such generation.

## Poll instead of watching

`GenerationWatch` is removed: poll `GenerationGet` on your own interval until the generation settles. A polled generation moves at the caller's pace; an unpolled one waits for the sweep, up to one `SWEEP_INTERVAL`.

## Stream the output as it is written

To show a generation's output while the provider writes it, submit it with `stream: true`, then call `GenerationStream` with its id. The stream forwards the provider's events, as sent, with their `sequence_number`, and ends after the terminal one. After a disconnect, open a new stream with `starting_after` set to the last sequence number you received. The provider streams a call for 5 minutes after its creation: past that, or for a generation not submitted with `stream`, the stream answers `FAILED_PRECONDITION`, and you read the result with `GenerationGet`. A streamed submit answers once the provider has begun the call, so it takes the provider's queue time. `stream` is part of the request: the same payload with and without it are two generations. A streamed generation is one provider call: a retryable provider failure settles it failed rather than retrying it, so resend it to run it again.

## Read usage off the responses

`UsageQuery` is removed. Each attempt's response carries the usage the provider reported for it: read it there before the attempts are purged with their generation. The service keeps its own permanent Usage Record of every answered attempt, which the caps sum, and exposes none of it through the API.

## Recreate the database

The migration history starts over in this release. No environment ran service-genai before it, so there is no data to carry over: start the `database` image on a fresh volume, then run the migrations job. A data directory from the earlier image is not portable to the new one, and lacks the settings the retention purge needs.

## Replace the configuration

| Removed                                                                                     | Replacement                                                                                          |
| ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `WORKER_ID`, `WORKER_INTERVAL`, `WORKER_LEASE`, `WORKER_BATCH_SIZE`, `WORKER_POLL_INTERVAL` | `CHECK_INTERVAL` (`2s`)                                                                              |
| `REAPER_INTERVAL`, `REAPER_GRACE`, `REAPER_BATCH_SIZE`                                      | `SWEEP_INTERVAL` (`1m`), `SWEEP_BATCH_SIZE` (`50`)                                                   |
| —                                                                                           | `MAX_ATTEMPTS` (`2`), replacing the request's `max_attempts`                                         |
| `RETENTION` default `168h`                                                                  | `RETENTION` default `6h`: a settled generation, its attempts and its request key are purged together |
| `GRPC_PING`                                                                                 | Nothing: the health check reports the server's status as it changes, with no refresh interval        |

`OPENAI_API_KEY` keeps its name and is now required: the server refuses to start without it. `GRPC_TIMEOUT_SHUTDOWN` now defaults to `8s`, inside Cloud Run's ten seconds between SIGTERM and SIGKILL. Keep any override under your orchestrator's kill delay.

## Settle generations on provider notifications (optional)

The new `rest` image checks a generation the moment its provider reports the call ended, instead of on the next poll or sweep. Deploy it publicly with `OPENAI_WEBHOOK_SECRET` and register the OpenAI webhook endpoint, as the [README](../../README.md#deploying) explains. Without it, polls and the sweep settle every generation as before.

## Status changes

`GENERATION_STATUS_ABANDONED` is removed. A generation whose process died is picked up by the next check instead.

## Roll out and verify

A rolling deploy is safe at any time: a check runs for seconds, and anything it did not finish is redone by the next one.

In a test environment, submit a generation, stop the server while it runs, start it again, and poll: the generation settles once, with one attempt per answered provider call.
