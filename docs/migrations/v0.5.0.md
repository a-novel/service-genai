# Upgrading to v0.5.0

No process holds a generation any more. Submitting starts the provider call, each `GenerationGet` checks a stale generation with the provider, and a sweep checks the generations nobody polled. The worker and the reaper are gone.

## Do I need to act?

**Required** for operators: the database schema is replaced, and the worker and reaper settings are removed.

**Recommended** for callers: poll `GenerationGet` (or keep a `GenerationWatch` open) while you wait. A polled generation moves at the caller's pace; an unpolled one waits for the sweep, up to one `SWEEP_INTERVAL`.

## Recreate the database

The migrations are replaced by a single baseline, `20261008191734_generations`. No environment ran service-genai before this release, so there is no data to carry over: recreate the database, or drop the `generations` and `generation_usage` tables and the `generation_status` type, then run the migrations job.

## Replace the configuration

| Removed                                                                                     | Replacement                                        |
| ------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| `WORKER_ID`, `WORKER_INTERVAL`, `WORKER_LEASE`, `WORKER_BATCH_SIZE`, `WORKER_POLL_INTERVAL` | `CHECK_INTERVAL` (`2s`)                            |
| `REAPER_INTERVAL`, `REAPER_GRACE`, `REAPER_BATCH_SIZE`                                      | `SWEEP_INTERVAL` (`1m`), `SWEEP_BATCH_SIZE` (`50`) |

`GRPC_TIMEOUT_SHUTDOWN` now defaults to `8s`, inside Cloud Run's ten seconds between SIGTERM and SIGKILL. Keep any override under your orchestrator's kill delay.

## Status changes

`GENERATION_STATUS_ABANDONED` is no longer produced. A generation whose process died is picked up by the next check instead.

## Roll out and verify

A rolling deploy is safe at any time: a check runs for seconds, finishes inside the shutdown budget, and anything it did not finish is redone by the next one.

In a test environment, submit a generation, stop the server while it runs, start it again, and poll: the generation settles once, with one usage row per provider call.
