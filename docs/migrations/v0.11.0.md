# Upgrading to v0.11.0

The migrations drop the generation columns and the payload table that v0.10 stopped using, and give the sweep a partial index of its own. Nothing changes for callers.

## Do I need to act?

**Required** for operators: deploy this release only once v0.10 runs everywhere. Its migrations run while the release before it still serves, and a v0.9.0 replica breaks on the drops. The retention purge keeps working throughout.

**No** for callers: the API is unchanged.

## Deploy after v0.10

The migrations drop `generations.checked_at`, `run_at`, `attempt`, `max_attempts` and `first_start_requested_at`, the `generation_payloads` table, and the indexes `generations_check_idx` and `generations_provider_call_idx`. A v0.10 replica names none of them, so it keeps serving while the migrations job runs. A v0.9.0 replica names them all, and its inserts and checks fail once they are gone. Confirm that every environment runs a v0.10 release before you run this release's migrations job.

## Operators

- Run the migrations job, then deploy the servers, as for any release.
- The retention purge stops counting payloads in its byte budget before the table goes, so the `pg_cron` job keeps succeeding. Its budget now counts the attempts' responses alone.
- The sweep's new index, `generations_sweep_idx`, builds concurrently, and the two old indexes drop concurrently, so writes to `generations` go on. A build or a drop that gives up on its lock is retried by the migrations job, which first drops what the failed run left behind.
- Dropping the table and the columns locks `generations` for the catalog change only, within the job's three-second lock wait. Nothing rewrites the table.

## Roll out and verify

To verify, check that the purge job still succeeds after the migrations:

```sql
SELECT
  status,
  return_message,
  start_time
FROM
  cron.job_run_details
WHERE
  jobid = (
    SELECT
      jobid
    FROM
      cron.job
    WHERE
      jobname = 'service-genai-purge-settled'
  )
ORDER BY
  start_time DESC
LIMIT
  5;
```

## Notes

The down migrations restore the schema exactly, but not the dropped data. The dropped columns come back with their defaults, `checked_at` and `run_at` at the instant of the rollback. The payload table comes back with an empty object for each generation.
