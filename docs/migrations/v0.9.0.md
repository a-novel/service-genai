# Upgrading to v0.9.0

The service sends each provider call once and never retries it. A failed generation says why in a new `failure_class`, and the caller decides whether to resend. A submit carries the caps of its user, and a new `UsageSummary` RPC reports the usage they count. Every poll of an unsettled generation checks it with the provider, and the sweep runs one leader at a time.

## Do I need to act?

**Recommended** for callers: resend failed generations yourself, reading their failure class, and send each user's caps with every submit. A caller that does neither keeps working: a submit without caps answers to the caps file, as before, but a call that fails is no longer retried for it.

**Required** for operators that set `CHECK_INTERVAL` or `MAX_ATTEMPTS`: the servers no longer read them, so remove them. The migration adds one nullable column and runs in seconds.

## Resend failed generations yourself

A start the provider turned away, and a call it failed retryably, used to run again inside the service. Now the generation fails on its first outcome, and `Generation.failure_class` says what happened:

| `failure_class`   | What happened                                                                         | Resend?                                                                          |
| ----------------- | ------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `REJECTED`        | The provider refused the request, such as an unknown model or an exhausted quota.     | No: fix the request first. The attempt holds the provider's error body.          |
| `PROVIDER_FAILED` | The provider accepted the call, then failed it, ran it too long, or lost its answer.  | Yes, if your user still wants it. The call was paid.                             |
| `NOT_STARTED`     | The provider never ran the call: never sent, rate-limited, or refused for a conflict. | Yes. It cost nothing. Space resends out, as for any rate limit.                  |
| `OUTCOME_UNKNOWN` | The provider may have accepted the call, and may still run it.                        | Not at once: the generation holds its purpose's concurrency slot for 15 minutes. |

A generation that failed before this release reads `GENERATION_FAILURE_UNSPECIFIED`. Resending a failed request runs it from scratch, as before:

```go
generation := response.GetGeneration()

if generation.GetStatus() == servicegenai.GenerationStatusFailed {
	switch generation.GetFailureClass() {
	case servicegenai.GenerationFailureRejected:
		// Report the provider's error body to whoever built the request.
	case servicegenai.GenerationFailureOutcomeUnknown:
		// Wait for the slot hold to end before resending.
	default:
		// Resend the same request, within your own rate limits.
	}
}
```

A generation holds one attempt. `attempts` keeps its type, and a generation an earlier release retried still lists both of its answers until the purge.

## Send each user's caps

`GenerationSubmitRequest.caps` limits the user on the request's purpose: a `concurrency`, and token `windows`, each a `Duration` with optional `input_tokens` and `output_tokens`. A limit left unset sets no limit, and empty caps set none beyond the ceiling. With caps, `user_tier` is ignored, and the service's ceiling bounds the user across every purpose instead of the caps file's global tiers. Caps stay out of the request's identity, so a resend under other caps is still a replay.

```go
request.Caps = &servicegenai.GenerationCaps{
	Concurrency: proto.Int32(2),
	Windows: []*servicegenai.GenerationCapWindow{
		{Duration: durationpb.New(5 * time.Hour), InputTokens: proto.Int64(2_000_000)},
		{Duration: durationpb.New(720 * time.Hour), OutputTokens: proto.Int64(5_000_000)},
	},
}
```

The service refuses caps with a negative limit, more than 10 windows, two windows of one duration, or a duration outside `(0, 8760h]`, with `INVALID_ARGUMENT`.

A refusal keeps its `RESOURCE_EXHAUSTED` code and its message. It now carries a `google.rpc.QuotaFailure` with one violation: its `subject` names the limits that refused, `purpose "<name>"`, `ceiling` or `global`, and its `description` the limit, such as `concurrency 2` or `input tokens over 5h`. A window's refusal adds a `google.rpc.RetryInfo` when the window frees usage at a known time, once its oldest usage leaves it:

```go
for _, detail := range status.Convert(err).Details() {
	switch detail := detail.(type) {
	case *errdetails.QuotaFailure:
		limit := detail.GetViolations()[0].GetDescription()
	case *errdetails.RetryInfo:
		retryAfter := detail.GetRetryDelay().AsDuration()
	}
}
```

`errdetails` is `google.golang.org/genproto/googleapis/rpc/errdetails`.

## Show the room left

`UsageSummary` takes an owner, a declared purpose and up to 10 windows. It answers the owner's generations in flight for the purpose, counted as a caps concurrency counts them, and the input and output tokens used in each window, in the request's order:

```go
summary, err := client.UsageSummary(ctx, &servicegenai.UsageSummaryRequest{
	OwnerId: ownerID,
	Purpose: "studio.generation",
	Windows: []*durationpb.Duration{durationpb.New(5 * time.Hour), durationpb.New(720 * time.Hour)},
})
```

## Poll at a pace you bound

A poll used to reach the provider at most once per `CHECK_INTERVAL`, so a finished call could show up that late. Every poll of an unsettled generation now asks the provider, and a poll made after the provider finished returns the settled generation. Bound your polling: once every one or two seconds per generation, and a rate limit per user.

A submit now waits for its call's id to be recorded. While a migration holds a lock on the table, that takes up to two minutes. Keep a submit's deadline at the 35 seconds a streamed submit needs, and resend on a deadline: the resend replays the generation.

## Operators

- Remove `CHECK_INTERVAL` and `MAX_ATTEMPTS`.
- The sweep runs one leader at a time, which holds a PostgreSQL advisory lock on a connection of its own. Run as many `sweep` replicas and schedules as you like: a run that finds the lock taken answers `{"checked": 0}` at once. The leader checks one generation fewer at once than its pool has connections, eight at most.
- The ceiling, in [`ceiling.config.yaml`](../../internal/config/ceiling.config.yaml), bounds a user under caps across every purpose: 8 generations at once and 500,000,000 input and 50,000,000 output tokens over 720 hours. Tune it from measured usage.
- The migration adds the `generation_failure` enum and the nullable `generations.failure` column. Its check scans the table once, under a lock held as long as the scan of a few hours of generations.
- The service no longer writes `generation_payloads`. The table and the retry columns stay until a later release removes them. Rolling the schema back past the migration that created the payload table fails once generations without a payload exist.

## Roll out and verify

Run the migrations job, then deploy the servers. While v0.8.x replicas still run, one of them may settle a v0.9.0 submit's start as unknown if its call id is not recorded within a minute: a write that waits on a lock that long is rare.

To verify, submit a generation and poll it: it runs at once, and settles within a poll of the provider finishing. A failed one carries its `failure_class`, and `UsageSummary` answers for its owner.
